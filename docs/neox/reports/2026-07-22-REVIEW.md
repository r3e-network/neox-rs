## Critical Issues

### CR-01: Blob and set-code transactions bypass Geth's block-level Envelope policy

**Files:** `crates/neox/evm/src/executor.rs:315`, `crates/neox/antimev/src/envelope.rs:43`
**Classification:** BLOCKER
**Issue:** Block execution calls the type-sensitive `is_envelope`, which excludes EIP-4844 and EIP-7702 transactions at `envelope.rs:44-45`. Pinned Geth's consensus execution path (`core/state_transition.go:375-393`) applies maximum gas, encrypted-gas, and Envelope-fee rules based only on the target and calldata; its transaction-type exclusion is limited to Envelope counting/decryption and txpool behavior. A post-Cancun blob or post-Prague set-code transaction with Envelope-shaped calldata can therefore execute in NeoX-Reth while Geth rejects the same block.
**Impact:** Deterministic block-validity disagreement and chain split.
**Fix:** Introduce a target-plus-calldata policy predicate for consensus execution and retain the type-sensitive predicate only for Envelope counting, decryption, and pool admission. Add differential block-import tests for EIP-4844 and EIP-7702 transactions covering maximum gas, encrypted gas, and Envelope fee.

### CR-02: Anti-MEV reconstruction signs stale next-consensus commitments

**Files:** `crates/neox/node/src/producer.rs:248`, `crates/neox/node/src/proposal.rs:348`, `crates/neox/node/src/reconstruction.rs:188`
**Classification:** BLOCKER
**Issue:** The outer pre-block computes `next_validators`, `next_dkg`, `extra_data`, and `mix_hash` from state produced by encrypted Envelope transactions. Reconstruction re-executes decrypted replacements and updates state, transaction, receipt, bloom, gas, and blob roots at `reconstruction.rs:195-209`, but never recomputes the fallback validator commitment or threshold-key commitment. A decrypted inner transaction can legally change Governance or KeyManagement state. Pinned Geth explicitly recomputes both commitments from `pre.finalState` in `consensus/dbft/dbft.go:589-609`.
**Impact:** The final state root describes one validator/DKG state while the signed header commits to another. Mixed clients reject the block, and a homogeneous deployment can initialize the next height with stale authority data.
**Fix:** After final execution, read Governance and KeyManagement through the reconstructed post-state, recompute `extra_data` and `mix_hash` with the active version/scheme rules, and replace `proposal.next_validators` and `proposal.next_dkg` before final signing. Add end-to-end reconstruction tests where decrypted transactions change each contract.

### CR-03: A malformed TPKE commitment can permanently halt a consensus height

**Files:** `crates/neox/antimev/src/tpke.rs:85`, `crates/neox/node/src/antimev.rs:210`, `crates/neox/node/src/antimev.rs:367`, `crates/neox/node/src/sync/anti_mev.rs:122`
**Classification:** BLOCKER
**Issue:** `TpkeCiphertext::verify` proves that the G1 random commitment and negated G2 commitment use the same scalar, but production Envelope classification only decodes subgroup-valid points and never calls it. An attacker can submit different valid nonzero scalars for those two points. Honest validators then precommit shares derived from the G1 point, while every threshold subset fails the proof against the unrelated G2 point at `tpke.rs:426-434`. Reconstruction retries only when the contribution count increases; after all seven contributions there is no possible progress.
**Impact:** A single validly signed user transaction can move a round to PreCommitted and leave it unable to construct or sign any final block. Pinned Geth appears to share this protocol-level vulnerability.
**Fix:** Verify the ciphertext relation before a proposal can reach Prepared/PreCommitted and deterministically reject the proposal or classify the transaction according to a coordinated protocol rule. Add a full-lifecycle test using subgroup-valid but mismatched commitments.

### CR-04: One peer's unverified status can disable dBFT indefinitely

**Files:** `crates/neox/network/src/handler.rs:469`, `crates/neox/node/src/sync/sidecar.rs:69`, `crates/neox/node/src/sync.rs:1933`
**Classification:** BLOCKER
**Issue:** The handshake checks network, genesis, and fork hash but accepts arbitrary head metadata. `network_ahead_of` treats any advertised V2 height or V1 total difficulty as authoritative. On connection, `sync.rs:1949-1957` deactivates dBFT, clears the round and pending proposal state, disarms its timer, and requests the arbitrary head hash. Engine rejection does not remove the stored status or reactivate consensus; recovery occurs only after disconnect or after local height overtakes the claim.
**Impact:** A same-network peer can advertise `u64::MAX`, keep the socket open, and remotely stop a validator from proposing or voting forever.
**Fix:** Drive dBFT suspension from validated downloader/engine progress rather than raw peer status. Require verifiable ancestry or corroborated progress, bound claims, penalize failed targets, and reactivate immediately when a requested target cannot be validated. Test a connected peer that advertises `u64::MAX` and never serves the target.

### CR-05: Pure canonical reverts leave dBFT on an orphaned head

**File:** `crates/neox/node/src/sync.rs:301`
**Classification:** BLOCKER
**Issue:** Reth explicitly represents a pure revert as `CanonStateNotification::Reorg { old, new }` with an empty `new` segment. `tip_checked()` then returns `None`, and lines 306-309 continue without clearing proposal state, rolling back total difficulty or beacon status, updating the dBFT height, or resetting the timer.
**Impact:** After an unwind, the node advertises an orphaned head and can keep signing or proposing at the wrong height against a different canonical state.
**Fix:** Handle the empty-`new` case by resolving the parent of the first reverted block as the new tip, loading its canonical total difficulty, clearing all in-flight state, updating beacon/dBFT height, and activating the correct round. Add a pure-revert notification integration test.

### CR-06: Fixed-arity RLP decoding amplifies a 4 MiB peer message into tens of MiB

**Files:** `crates/neox/network/src/dbft.rs:122`, `crates/neox/network/src/dbft.rs:442`, `crates/neox/network/src/dbft_payload.rs:86`
**Classification:** BLOCKER
**Issue:** `DbftConsensusData::decode` calls `Header::decode_raw`, which first allocates a `Vec<&[u8]>` entry for every child and only then checks that exactly five fields exist. An ordinary peer can self-sign an outer `DbftMessage` whose data is a near-4 MiB list of millions of empty items. Witness recovery succeeds for the attacker's declared sender, allocation happens in `validate_message`, and membership is checked only afterward at `dbft.rs:474-495`. The same raw-list pattern appears in fixed-arity typed payloads.
**Impact:** One bounded wire frame expands to roughly 64 MiB or more of pointer storage; concurrent peers can exhaust validator memory before authorization.
**Fix:** Decode list headers and the permitted fields sequentially from a bounded payload, rejecting as soon as an extra item is encountered. Apply the bounded decoder to consensus data, prepare request, precommit, and recovery payloads, and add many-empty-item adversarial tests.

### CR-07: Unbounded Beacon queues retain attacker-controlled 10 MiB payloads

**Files:** `crates/neox/network/src/handler.rs:228`, `crates/neox/network/src/handler.rs:293`, `crates/neox/network/src/handler.rs:518`, `crates/neox/node/src/sync.rs:158`, `crates/neox/node/src/sync.rs:1987`
**Classification:** BLOCKER
**Issue:** Every decoded Beacon message is sent through an unbounded event channel. The sole consumer processes events serially and awaits propagated-block engine validation inline. A peer can continue enqueueing valid decoded messages, including owned block packets up to the 10 MiB frame limit, while the consumer waits on engine, disk, or transaction work. No count, byte budget, per-peer quota, or transport backpressure bounds retained data.
**Impact:** Remote memory exhaustion; the same backlog also delays dBFT messages and timers enough to disrupt consensus liveness.
**Fix:** Replace inbound event transport with bounded, byte-aware queues; coalesce/drop gossip, limit per-peer in-flight work, and apply backpressure or disconnect on saturation. Move block import behind a separately bounded worker so the consensus event loop never awaits it inline. Test queue bounds and timer progress under a large-message flood.

### CR-08: The first relay can pin transaction recovery and force repeated view changes

**Files:** `crates/neox/network/src/dbft.rs:497`, `crates/neox/node/src/sync.rs:525`, `crates/neox/node/src/proposal.rs:60`, `crates/neox/node/src/sync/proposal_recovery.rs:144`
**Classification:** BLOCKER
**Issue:** Global hash deduplication records only the first transport source for an otherwise valid signed proposal. Transaction recovery permanently binds missing hashes to that peer and rejects responses from any other peer. If the first relay lacks Beacon/2, `dispatch` logs a failed send but leaves the request pending; later copies from the honest primary or another relay are suppressed by the network cache. A malicious relay can race each new-view proposal and withhold its transactions.
**Impact:** A non-validator relay can repeatedly force `TransactionNotFound` timeouts and prevent a victim validator from preparing otherwise valid proposals.
**Fix:** Track all relay sources independently of content deduplication, fail over across Beacon peers, and remove/requeue pending state on failed sends, empty replies, disconnects, and deadlines. Add a malicious-first/honest-second recovery test.

### CR-09: Custom dBFT coinbase configuration is parsed but ignored

**Files:** `crates/neox/chainspec/src/config.rs:39`, `crates/neox/consensus-engine/src/lib.rs:163`, `crates/neox/evm/src/config.rs:56`, `crates/neox/evm/src/config.rs:127`
**Classification:** BLOCKER
**Issue:** `NeoXConsensus` validates every child against the global canonical reward address, and EVM construction overwrites the beneficiary with the same global address. The parsed `dbft.coinbase` is never used. Pinned Geth validates against `c.config.Coinbase` and rejects only an empty configured value.
**Impact:** A Geth-compatible custom chain with a noncanonical configured coinbase splits immediately: NeoX-Reth rejects Geth blocks and produces headers that Geth rejects.
**Fix:** Validate and produce with `chain_spec.neox.dbft.coinbase` throughout consensus, EVM environment construction, and proposal building. Reject the zero address in `from_genesis` and add a noncanonical custom-chain differential test.

### CR-10: Duplicate genesis validators allow one key to satisfy a five-of-seven seal

**Files:** `crates/neox/chainspec/src/config.rs:23`, `crates/neox/chainspec/src/spec.rs:65`, `crates/neox/consensus/src/validation.rs:70`
**Classification:** BLOCKER
**Issue:** Genesis validation checks only that exactly seven standby entries exist; it does not reject zero or duplicate addresses. ECDSA verification sorts the allowed entries and recovered signers, then consumes one allowed slot per signature. Five copies of one address in the validator list therefore authorize five copies of the same signature. This conflicts with `DbftRoundState::new`, which treats duplicates as invalid, so the node will not participate locally but will still accept externally supplied headers under the weakened seal rule.
**Impact:** A custom chain can silently reduce its nominal five-of-seven block authority to one private key, while NeoX-Reth's local validator state fails to start.
**Fix:** Reject zero and duplicate standby validators in `NeoXChainSpec::from_genesis`, defensively reject duplicate validators/signers during seal verification, and add a header test containing one signature repeated five times.

## Warnings

### WR-01: Proposal validation rejects Geth-valid future timestamps

**File:** `crates/neox/consensus-engine/src/lib.rs:179`
**Classification:** WARNING
**Issue:** The unsealed PrepareRequest path applies the local wall-clock check before structural validation. Pinned Geth gates that check on `isSealed` and deliberately omits it for proposals. A proposal one second ahead of a backup's clock is rejected even though it is valid once sealed/imported.
**Fix:** Split sealed-header and proposal validation so only sealed imports use `validate_present_timestamp`; retain parent-relative timestamp rules for proposals. Add skewed-clock mixed-client tests.

### WR-02: Zero-period dBFT configurations pass chain-spec construction

**Files:** `crates/neox/chainspec/src/config.rs:35`, `crates/neox/chainspec/src/spec.rs:58`, `crates/neox/node/src/sync.rs:129`
**Classification:** WARNING
**Issue:** A custom genesis can set `period` to zero. Startup succeeds and creates zero-duration consensus timers, driving immediate view changes and eventual loss of liveness. Pinned Geth rejects zero-period dBFT during engine construction.
**Fix:** Reject `period == 0` with a typed `NeoXChainSpecError` and a regression test.

### WR-03: Pool policy and account checks can observe different heads

**File:** `crates/neox/node/src/pool.rs:64`
**Classification:** WARNING
**Issue:** The standard validator has already obtained a state snapshot for nonce, balance, and bytecode, but the additional policy hook ignores its `_account_state` and independently calls `provider.latest()`. A head change between those reads mixes two canonical states in one validation decision. Pinned Geth passes one state snapshot through all stateful validation.
**Fix:** Expose storage reads through the same pinned validation state, or pin a block hash/provider once for the full operation. Add a controlled head-change test.

### WR-04: Valid Geth genesis files with one omitted dBFT header field are rejected

**File:** `crates/neox/chainspec/src/spec.rs:72`
**Classification:** WARNING
**Issue:** NeoX-Reth requires `extraData` and `mixHash` to be both present or both absent. Geth synthesizes each missing field independently, so custom genesis files accepted by the oracle are rejected here.
**Fix:** Synthesize each missing component independently using the configured standby set, then validate consistency after both values exist. Cover both one-field-omitted cases.

### WR-05: Public `DbftExtra` values can panic or emit invalid wire layouts

**File:** `crates/neox/consensus/src/extra.rs:161`
**Classification:** WARNING
**Issue:** Public enum variants permit V1/V2 ECDSA without a fallback hash and threshold signatures with V0. `encode` panics for the former at line 276 and emits a layout that decodes as incompatible V0 ECDSA for the latter.
**Fix:** Hide variants behind checked constructors or replace `encode` with a fallible `try_encode` that enforces version, scheme, fallback, validator-count, and signature-count invariants.

### WR-06: Future-view messages are cached before the round can accept them

**Files:** `crates/neox/network/src/dbft.rs:654`, `crates/neox/node/src/validator.rs:568`, `crates/neox/node/src/sync.rs:555`
**Classification:** WARNING
**Issue:** The network cache permanently deduplicates a cryptographically valid message before the state machine evaluates its view. Prepare/response or future precommit/commit messages are rejected as `WrongView`; after the local view advances, retransmission of the identical valid message is suppressed.
**Fix:** Buffer bounded future-view messages and replay them when the view advances, or mark delivery complete only after state-level acceptance. Add an early-next-view message test.

### WR-07: The late-message shortcut bypasses authentication and is broader than Geth

**File:** `crates/neox/network/src/dbft.rs:631`
**Classification:** WARNING
**Issue:** Messages whose validity end equals the current height or `current - 1` return success before witness, sender, inner-payload, or typed-payload validation. Any peer can repeatedly send malformed late traffic without disconnect or accountability. Pinned Geth authenticates first and only ignores the exact current-height case.
**Fix:** Verify the witness and structural message before applying the shortcut, and restrict it to the oracle's exact height condition.

### WR-08: Beacon handshake ignores `ForkID.next`

**File:** `crates/neox/network/src/handler.rs:498`
**Classification:** WARNING
**Issue:** Compatibility is reduced to membership of the remote current hash in a locally reachable hash set. Two nodes with the same past but incompatible future schedules share that hash and connect because the remote `next` field is never checked; they discover incompatibility only after divergence.
**Fix:** Validate future-fork compatibility as well as current-hash membership, using schedule-aware semantics that support Neo X's mixed block/time ordering. Add equal-current-hash/different-next tests.

### WR-09: Sidecar backfill has no retry or peer failover

**Files:** `crates/neox/node/src/sync/sidecar.rs:111`, `crates/neox/node/src/sync/sidecar.rs:327`, `crates/neox/node/src/sync/sidecar.rs:363`
**Classification:** WARNING
**Issue:** Expiration only drops pending state, responses are removed before validation, partial batch suffixes are not requeued, and duplicate announcements are suppressed while a request is pending. A selected peer that times out or returns invalid/partial data can leave finalized sidecars unavailable even when another serving peer is connected.
**Fix:** Preserve alternate sources and retry missing hashes on timeout, invalid response, partial batch, and disconnect; penalize failed peers and drive expiry from an independent timer. Add two-peer failover tests.

### WR-10: Validator rotation does not purge messages from removed validators

**Files:** `crates/neox/network/src/dbft.rs:356`, `crates/neox/network/src/dbft.rs:368`
**Classification:** WARNING
**Issue:** Height updates evict only expired messages, and activation replaces the validator set without purging cached senders. A currently authorized validator can cache a far-future message, leave the set, and still have that now-unauthorized payload served to peers, which then reject or disconnect.
**Fix:** Atomically update height and validators and purge every cached message whose sender/index is no longer authorized. Add a rotation test with a retained future message.

### WR-11: Decrypted private transaction plaintext is not wiped

**Files:** `crates/neox/antimev/src/tpke.rs:359`, `crates/neox/node/src/antimev.rs:401`
**Classification:** WARNING
**Issue:** AES decryption returns a plain `Vec<u8>`, and `decrypt_transaction` drops it normally after EIP-2718 decoding. Signed private transaction bytes can remain in allocator memory during the confidentiality-sensitive precommit window.
**Fix:** Return or immediately wrap plaintext in `Zeroizing<Vec<u8>>`, and wipe key-derivation/AES temporaries where possible.

### WR-12: A valid DKG polynomial can panic on a zero evaluation

**Files:** `crates/neox/antimev/src/dkg.rs:189`, `crates/neox/antimev/src/dkg.rs:264`, `crates/neox/antimev/src/dkg.rs:562`
**Classification:** WARNING
**Issue:** `evaluate` returns `Result` but converts through `secret_from_fr`, which `expect`s that the result is nonzero. Nonzero canonical coefficients can mathematically cancel at any validator point. Such coefficients can enter through migrated/persisted state, and PVSS generation then panics at line 278 instead of returning an invalid-state error.
**Fix:** Use `try_secret_from_fr`, make `generate_pvss_with_randomizer` fallible, propagate `InvalidScalar`, and test a cancellation polynomial.

### WR-13: DKG secret erasure is not cancellation- or optimizer-safe

**Files:** `crates/neox/node/src/dkg_prover.rs:102`, `crates/neox/node/src/signer.rs:96`, `crates/neox/node/src/signer.rs:270`
**Classification:** WARNING
**Issue:** The prover request contains hex-encoded raw shares in a plain `Vec<u8>` and wipes it only after an `await`; aborting or dropping the future skips the wipe. `DkgPrivateShare::drop` uses ordinary `fill(0)`, which is not guaranteed against dead-store elimination, and invalid replacement inputs remain bare arrays on early return.
**Fix:** Put serialized requests and input arrays into `Zeroizing` before the first fallible/async operation, and derive `Zeroize`/`ZeroizeOnDrop` for all private-share wrappers. Add cancellation and validation-error-path tests.

### WR-14: DKG replay cannot recover a store more than one round out of date

**File:** `crates/neox/node/src/dkg_replay.rs:239`
**Classification:** WARNING
**Issue:** Every replay entry point requires `canonical_round == store.round() + 1`. There is no rollback or fast-forward/reset primitive in the node crate. A validator offline for two epochs is permanently rejected, and a canonical rollback can leave the local store ahead. Pinned Geth resets stale stores to the retained prior round and reconstructs the latest canonical material.
**Fix:** Add crash-safe round journaling/rollback plus a baseline-compatible reset-and-rebuild path (or complete historical replay), and test both an ahead-by-one rollback and a behind-by-multiple-rounds restart.

### Additional hardening

- Network admission now reserves count, byte, peer, and channel capacity before cache insertion, so
  queue saturation cannot strand a message as an undelivered cache hit. Known Announce hashes use
  constant-time cache membership checks, while an explicit full signed retransmission remains
  deliverable. Droppable Beacon announcements have a separate quota that preserves required-event
  slots and a maximum-frame byte reserve.
- Legacy round-key loading binds `<round>.key` and `<round-1>.key` to the exact canonical head,
  native Governance ordering, and all seven canonical share/reshare PVSS evaluations. It fails
  closed on notification gaps, reorgs, or continuity violations; the managed keystore is the
  in-process branch-recovery path.
- The managed DKG runtime reconciles settled signer shares before active task work, preserves those
  shares when active reads/replay/proving fail, detects locally completed canonical tasks, and
  removes its stale local pool transactions on invalidation or expiry. A periodic head check repairs
  dropped canonical notifications. During active rounds it executes the proxy-backed canonical
  `ZK_VERSION()` getter through the Neo X EVM and suspends task work on call failure or configured
  version mismatch.
- Transaction-pool admission performs standard stateless and stateful validation before Neo X
  Policy reads or TPKE pairing, lazily reuses one pinned state snapshot for valid batches, and marks
  decoded commitment mismatches as permanently bad transactions. Block production independently
  rechecks and evicts a malformed resident Envelope so it cannot force repeated view changes.
- The external prover is restricted to a pinned static Linux ELF helper and manifest-hashed
  network artifacts, with bounded execution, output limits, and secret zeroization. On Linux the
  supervisor owns the child and process-group guard together, so explicit Drop kills the complete
  group before releasing the child even if the supervisor future is never polled; normal completion
  or cancellation observes the direct child without reaping it, then explicitly reaps the leader
  and joins both output readers. Validator startup waits for initial canonical DKG reconciliation
  before reporting readiness.
- Descendant catch-up uses source-aware claims, a fair unique-hash queue, and one request budget and
  cooldown per authoritative canonical anchor. Peer rotation, forged heights, disconnects, and stale
  completions cannot reset the budget or revive terminal targets. A dedicated capacity-one worker
  completes forkchoice requests single-flight outside the consensus event loop, so canonical and
  dBFT processing remain responsive while the engine imports a remote descendant.
