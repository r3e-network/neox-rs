# Neo X client internal audit — 2026-07-19

Scope: the `neox` branch implementation of the Neo X execution and full-node protocol
(`crates/neox/*`, `bin/neox-rs`). This is an internal engineering audit, not the independent
protocol/security review still required before any validator or MainNet release claim.

## Verification performed

All commands use the stable toolchain (workspace MSRV is rustc 1.95; the default nightly on the
build host is 1.91 and is too old — see [`../../..`](../source-baseline.toml)).

| Check | Command | Result |
|---|---|---|
| Build | `cargo +stable build -p neox-rs` | pass |
| Unit/integration tests | `cargo +stable test` across all `reth-neox-*` crates and `neox-rs` | pass |
| Lints | `cargo +stable clippy --all-targets` on the neox crates and `neox-rs` | clean |
| Formatting | `cargo +nightly fmt --all --check` | clean |

| Genesis oracle | computed `genesis_hash()` vs `NEOX_MAINNET_GENESIS_HASH` / `NEOX_TESTNET_GENESIS_HASH` | match (asserted by chainspec tests) |

The `genesis_*.json` files in `crates/neox/chainspec/res` are Reth serializations and intentionally
do not share a byte-for-byte SHA-256 with the upstream Geth `config/genesis_*.json` recorded in
`source-baseline.toml`; the binding invariant is the computed genesis **block hash**, which matches.

A full-workspace `--all-targets` build additionally requires `llvm-config` because
`crates/ethereum/evm` pulls `revmc` under its optional `jit` feature. That is upstream Reth code; no
neox crate depends on `revmc`, and every neox target compiles under the clippy run above.

## Consensus-safety review

Three independent adversarial reviews (consensus/crypto, DKG validator runtime, network/sync) plus
a manual pass over chainspec, EVM, pool, engine, signer, and system-contract code found **no
consensus-safety defect**: no path accepts an invalid block as canonical, and no path mutates dBFT
round state before cryptographic authentication. Specifically confirmed correct:

- ECDSA dBFT quorum: `decode_ecdsa` requires exactly `bft_honest_node_count` (2f+1 = 5 of 7)
  signatures via a strict length check, and `verify_ecdsa_signatures` proves each recovered signer
  is a distinct authorized validator via the sorted monotonic merge.
- TPKE / DKG cryptography: BLS subgroup and scalar validation, the EIP-2537↔blst Fp2 byte-order
  swap, Lagrange interpolation (with and without the scaler), the domain-separation tag, and the
  `blst_fp12` pairing identity check are all correct and match the embedded Geth-derived vectors.
- Header/consensus integration: signature verification runs in `validate_header_against_parent`;
  the Policy-governed base fee, governance coinbase, and version/threshold activation gating are
  enforced; `validate_parent_reseal` re-validates the alternate witness.

## Findings (liveness / robustness hardening, pre-release validator runtime)

None of these affect block validity or state-root correctness. They are fault-tolerance gaps in the
validator orchestration layer and map onto the private-network fault gates already listed as
remaining release work.

### Fixed in this change

- **NX-1 (was: unbounded proposal-transaction re-requests).** `ProposalTransactionSync::supply`
  re-issued a fresh `GetTransactions` whenever any transaction was still missing, so a peer that
  answered with an empty (no-progress) response could drive unbounded requests until the view-change
  timeout. A pending entry always has at least one missing transaction, so a response supplying none
  now returns `DbftProposalError::EmptyTransactionResponse` and abandons recovery, reaching the same
  view-change outcome without the request amplification. Regression test:
  `proposal::tests::abandons_recovery_on_a_no_progress_transaction_response`
  (`crates/neox/node/src/proposal.rs`). The partial-progress path was already bounded by
  `MAX_PROPOSAL_TRANSACTIONS`.

### Open — require the live fault-gate harness to validate a fix safely

These change consensus-participation timing or crash-safe keystore state. Fixing them blind, without
the private-network reorg/view-change/restart harness, risks regressing correct behavior, so they
are recorded here for the corresponding release gates rather than patched speculatively.

- **NX-2 (MEDIUM, liveness/DoS).** `crates/neox/node/src/sync.rs` computes `network_is_ahead`
  purely from peer-advertised, unvalidated `head_number` / `total_difficulty`, stored once at
  `BeaconEvent::Established` and never refreshed (only `Disconnected` removes it). A single peer
  advertising `head_number = u64::MAX` (or V1 `total_difficulty = U256::MAX`) keeps `network_is_ahead`
  true for the life of the connection, permanently calling `dbft.deactivate()` and stopping the
  validator's consensus participation, with no peer accountability for failing to serve the claimed
  target. Belongs to the restart/backfill fault gate; a fix needs peer status refresh and
  drop-on-non-delivery, validated against the sync driver's intended behavior.

- **NX-3 (MEDIUM, liveness).** `bin/neox-rs/src/dkg_runtime.rs` `reconcile_settled_round` bails
  whenever the local keystore round is ahead of the canonical round. The encrypted keystore round is
  monotonic (`on_epoch_change` only increments; `revert_round` clears sub-state but never
  decrements), so a canonical reorg that reverts an epoch-settlement block leaves `local_round >
  contract_round` and aborts every heartbeat until the chain independently re-settles the round.
  Requires a keystore round-rollback path; validate under the reorg fault gate. Reachability depends
  on whether dBFT finality permits an epoch-boundary reorg.

- **NX-4 (MEDIUM, concurrency).** `BeaconEvent::NewBlock` is imported by awaiting
  `import_propagated_block` inline inside the `tokio::select!` loop (`sync.rs`), unlike committed-block
  import and proposal verification which are spawned. A propagated-block flood serializes engine
  round-trips through the consensus loop, delaying dBFT message and timer handling. Attackers cannot
  force expensive execution (that needs a valid 2f+1 seal). The fix (spawn the import like the other
  paths) is a concurrency change to the import path and needs live validation of ordering.

- **NX-5 (MEDIUM, operational).** A node whose keystore is more than one round behind canonical
  (`reconcile_settled_round` requires `local_round + 1 == contract_round`) bails every heartbeat with
  no multi-round catch-up. This is partly by design — the supported bootstrap is Geth-keystore
  migration (which preserves the round) or genesis-time operation — but there is no in-code
  reconciliation for a validator offline for more than one full epoch.

### Open — low severity, bounded / self-healing

- **NX-6 (LOW).** `dkg_runtime.rs`: if `install_signer_shares` fails after the epoch is persisted,
  the equal-round early return means it is not retried; the signer can lack the new epoch's shares.
  Unlikely for a validly settled epoch (a valid aggregated share is a valid scalar; a non-member
  installs `(None, None)` without validation).

- **NX-7 (LOW).** `dkg_runtime.rs` / `dkg_transaction.rs`: a task that expires with an already
  submitted-but-unmined transaction leaves a nonce gap that stalls later same-epoch tasks until the
  stuck transaction mines or the per-epoch `machine.reset` rebuilds the queue. Bounded and
  self-healing per epoch.

- **NX-8 (LOW).** `crates/neox/network/src/dbft_payload.rs`: `DbftRecoveryMessage::decode` fully
  decodes each `Vec<…Compact>` before `validate_limits()` enforces `MAX_RECOVERY_PAYLOADS`, allowing
  bounded (~10×) transient decode-time heap amplification within the 4 MiB `dbft/0` frame, freed per
  message. Reordering the codec risks wire-compat subtleties; deferred.

## Conclusion

The neox implementation is code-complete and its consensus-safety core is verified against the Geth
behavior oracle. The remaining work is the live private-network fault-gate validation already named
in [`../README.md`](../README.md) (explicit view-change, prover delay, transaction replacement,
Anti-MEV decryption, reorg) plus the independent protocol/security review — the same gates under
which the open findings above should be resolved.
